# Аудит: исправления v0.2.1

Проверены импорт, агрегация, деньги, Telegram, диагностика и связанные маршруты.
Ожидаемая нагрузка: небольшой магазин с несколькими операторами. Изменения
проверены регрессионными тестами на PostgreSQL и SQLite; вызовы Telegram замоканы.

## Статус находок

| Находка | Исправление |
| --- | --- |
| Потеря ручных цен | Сводные карточки не удаляются при агрегации. |
| Устаревшая цена поставщика | Используется последний успешно обработанный прайс поставщика за текущий день. Это полный снимок: исчезнувшие из него товары теряют предложение поставщика. |
| Повторный/частичный импорт | POST, блокировка прайса, проверка обработанного статуса, валидация и транзакция всех записей. Ошибка откатывает импорт. |
| Параллельные пересборки | Общая блокировка CatalogRebuildMutex защищает пересборку предложений. |
| Ошибки сумм | Decimal, пробелы и неразрывные пробелы, копейки, валюта. Модель и память не принимаются за цену. |
| Преждевременное подтверждение webhook | Уникальный update_id в БД, блокировка и отметка завершения после успешной обработки. После ошибки событие можно повторить. |
| Расхождение polling/webhook | Один обработчик и одна проверка повторов; offset polling меняется после успеха. Старые minimal-кнопки поддерживаются. |
| Заглушка прайса в боте | Кнопка отправляет актуальную сохраненную публикацию. Обычная переписка не порождает кнопок и подтверждений на каждое сообщение. |
| Истекший callback | Просроченное подтверждение кнопки не отменяет действие и не блокирует очередь. |
| Гонка прочтения | Счетчик сбрасывается только при неизменившемся updated_at заявки. |
| Блокировка HTTP очисткой | Healthcheck не вызывает Telegram, очистка из sidebar/webhook запускается в отдельном потоке. Задачи хранятся в БД. |
| Неуспешная очистка блокирует очередь | Задержка повторов увеличивается; после пяти ошибок задача остается для диагностики, но не блокирует новые. |
| Частично опубликованный прайс | ID успешных частей сохраняются при штатной ошибке отправки; старый прайс остается активным. Частичные сообщения убираются при следующей успешной публикации. |
| Одновременные публикации | Singleton-блокировка на PostgreSQL сериализует публикации. |
| Утечка диагностики | Страницы доступны staff, короткие секреты маскируются. |

## Удалено

Удалены дублирующий минимальный обработчик и его вспомогательные функции из
views.py, недостижимые функции закрытия/клавиатуры из telegram_bot.py,
прототип ui-preview вместе с маршрутом. Сохранены рабочие обработчики и совместимость
с кнопками в уже отправленных сообщениях.

## Проверки

Тесты охватывают повторы, откат после ошибки, одну заявку для продолжения диалога,
закрытие, очистку, денежные форматы, замену предложений, сохранение ручных цен,
частичную отправку, offset и гонку прочтения. PostgreSQL-тесты дополнительно
проверяют параллельную обработку одного update и блокировки публикации/каталога.

## Реальные ограничения

- Telegram Bot API не поддерживает ключ идемпотентности sendMessage. Если Telegram
  принял сообщение, но соединение оборвалось до ответа, повтор может создать дубль.
  БД устраняет повторы успешно завершенных событий, но не дает гарантии exactly-once
  для внешних отправок. Аварийное завершение процесса между API и фиксацией БД имеет тот же предел.
- На бесплатном Render фоновый поток живет только пока жив web-процесс. Без трафика
  нельзя обещать очистку ровно через минуту. Есть ручная команда
  python manage.py process_telegram_cleanup и обработка очереди в polling.
- Гарантии блокировок проверены на PostgreSQL. SQLite предназначена для одиночного
  локального просмотра, а не для нескольких рабочих процессов.
- Реальный Telegram, Render и независимое сканирование зависимостей на уязвимости
  не проверялись. Отказоустойчивость хостинга и постоянное хранение медиа остаются
  отдельными задачами эксплуатации.

Вердикт: подтвержденные находки аудита закрыты в исходниках и регрессионных тестах.
Перед подключением реального магазина нужен сквозной прогон с тестовым ботом.
